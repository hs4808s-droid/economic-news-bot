# "3분 브리핑" 새 구조 설계안 (적용하지 않음 — 2026-10-17)

견본: `docs/preview/2026-10-17-brief.html` (생성: `node scripts/build_brief_preview.js`). Claude 호출은 견본용 1회뿐이고 매일 파이프라인(`run_daily.sh`·`daily.yml`)은 건드리지 않았다.

## 1. 2단계(분석)+3단계(리포트) → 1회 호출
- **현재:** 2단계가 `calendar.json`(116KB 전체)·직전 리포트(59KB)·1_collect(25KB)를 읽고 27KB 분석을 쓰고, 3단계가 다시 1_collect·2_analysis·`tickers.json`(27KB)·`calendar.json`을 읽어 28KB 본문(+코드가 표를 끼워 52KB)을 쓴다. 같은 입력을 두 번 읽고, 분석문을 리포트로 한 번 더 옮겨 쓴다.
- **제안:** 한 번의 호출이 `COLLECT`(1_collect.md) + `CALENDAR_FACTS`(코드가 원장에서 만든 8KB 요약) + `WATCHLIST` + `TICKER_NAMES`(본문에 나온 티커만)를 받아 **JSON 하나**(한 줄·세 문장·이야기 ≤3·관심 종목·주의 1줄)만 낸다. 표·섹터·일정은 전부 코드.
- **프롬프트 초안:** `prompts/preview_brief.md` (견본에서 실제로 사용). 핵심 규칙: 본문 1,500자 안팎, 숫자는 입력 그대로, 일정·실적 숫자는 CALENDAR_FACTS만, 예상값 없는 지표에 상회/하회 금지, 금리는 FRED만, 이야기마다 "무슨 일→왜→종목→다음 확인" 4요소.
- **유지할 것:** 전일 판단 점검이 필요하면 직전 리포트 전체 대신 코드가 뽑은 "직전 한 줄·TOP 3"(≈1KB)만 입력에 넣는다. ★ 등급·확신 수준은 `stories[].conf` 필드로 필요 시 추가 가능(견본에는 없음).
- **위험:** 분석 깊이가 줄어든다(AI 밸류체인 카드·섹터 카드 등). 상세가 필요한 독자를 위해 현재 구조의 풀 리포트를 접힌 영역/별도 페이지로 일정 기간 병행하는 안을 권한다(결정 사항).

## 2. Collect 단계 검색 횟수 상한
- 현재는 상한이 없다(프롬프트가 15개 섹션을 요구). 제안: **WebSearch 최대 14회**, 초과 시 해당 항목은 N/A.
  | 용도 | 상한 | 비고 |
  |---|---|---|
  | 연준·거시 뉴스 | 3 | 발표 당일 지표 포함 |
  | 특징 종목(±5%) | 3 | 0_data.md 의 등락률로 대상을 코드가 미리 추림 |
  | AI 공급/수요·CAPEX | 3 | |
  | 컨센서스 선수집(발표 1~3일 전 ★★ 지표) | 3 | 이번에 추가된 규칙 |
  | 수급·기타 | 2 | |
- 검색 대신 **코드로 옮길 것:** Form 4(SEC EDGAR API로 관심 종목 직접 조회), ETF 자금흐름 일부, 시총 상위 10 가격 이슈(Finnhub 뉴스). 검색 1회의 컨텍스트는 대략 3~5K 토큰이고 이후 모든 턴에서 다시 읽히므로, 상한이 가장 큰 절감 레버다.

## 3. 섹터 카드 → 코드 생성
- 현재 `## 3. 섹터 카드`는 LLM이 15개를 쓰고(8.5KB) 지수 숫자와 어긋날 위험이 있다.
- 제안: 0_data.json 의 `group==='sector'` 15개 ETF를 1D/5D/1M/YTD 숫자로만 표시(견본 `sectors()`). 섹터 뉴스 한 줄이 필요하면 Finnhub 수집분 중 해당 ETF 대표 종목의 헤드라인 1개를 코드가 붙인다. LLM은 `stories`에서 필요한 섹터만 언급.
- 효과: 출력 8.5KB(≈4.3K 토큰) 삭제, 섹터 숫자 불일치 원천 제거.

## 4. 티커 표기 단순화
- 규칙: **`마이크론(MU)`** — 이름 뒤 괄호에 티커만. 섹터는 본문에서 뺀다(섹터는 사이트 티커 마스터·툴팁에서만). 이름이 티커와 같으면 티커만(`AMD`). 견본에서 코드 `fixName()`이 `AMD(AMD)` 같은 중복을 정리한다.
- 검증기 변경안: `T(이름·섹터)` 첫 등장 검사(현재 기존 3건 경고의 주범)를 "이름(T)" 형식 검사로 교체하고, 이름은 `tickers.json`과 글자 일치만 요구.
- 이미 쌓인 과거 리포트는 건드리지 않는다(새 형식은 신규 리포트부터).

## 5. 토큰·시간 측정과 예상 절감 (2026-10-17 실행분 기준)
측정 방법: 견본 호출을 `claude -p --output-format json` 으로 실행해 `usage` 를 읽음(실측). 현재 파이프라인은 단계별 usage 가 로그로 남지 않아 **파일 크기(바이트)×0.5 토큰** 으로 환산했다(실측 환산비: 입력 0.52, 출력 0.50 토큰/바이트). 검색 맥락(Collect)은 측정 불가라 제외.

| 구분 | 입력 토큰(캐시 포함) | 출력 토큰 | 시간 |
|---|---|---|---|
| 현재 2단계 분석 (추정) | ≈107K + 시스템 51K | ≈13.9K | ≈5분(문서 내 생성시각 기준 추정) |
| 현재 3단계 리포트 (추정) | ≈104K + 시스템 51K | ≈14.1K | ≈5분 |
| **현재 2+3 합계** | **≈313K** | **≈28K** | **≈10분** |
| **새 구조 1회 호출 (실측)** | **70.3K** (콘텐츠 19K + 시스템 51K) | **2.25K** (사고 0.85K 포함) | **26초** (API 26.3s) |
| 절감 | **−78%** | **−92%** | **−95%** |

- 실측 비용(견본 1회): total_cost_usd ≈ $0.248.
- 시스템 오버헤드 51K(Claude Code 기본 프롬프트·도구 정의)는 호출 수에 비례하므로, 호출을 3회→2회(Collect + 통합)로 줄이면 그만큼 추가 절감(약 51K).
- 전체 파이프라인(Collect 포함)은 검색 맥락을 측정하지 못해 정확한 총량은 말할 수 없다. Collect 에 14회 상한을 걸고 Form 4·시총 상위를 코드로 옮기면 Collect 쪽도 수십 % 줄 것으로 **추정**한다(미측정).
- 파이프라인 전체 시간은 GitHub Actions 기준 18.5분(10/17 실행)·25.7분(10/16 실행)이었고, 2+3 단계가 사라지면 약 10분 단축이 가능하다.

## 6. 적용 순서 제안 (승인 시)
1. 병행 운영: 기존 풀 리포트 유지 + 브리핑 페이지 추가 게시(메일은 브리핑 우선).

3. 1주 병행 후 풀 리포트 2·3단계를 중단할지 결정.
